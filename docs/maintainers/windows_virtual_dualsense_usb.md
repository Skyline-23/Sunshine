## Problem Statement

Sunshine currently supports Windows virtual gamepads through ViGEm only. In practice, that means:

- Windows can present `x360` and `ds4`-style virtual controllers.
- Windows cannot present a native USB DualSense device.
- DualSense-only host behaviors cannot be reproduced reliably by merely proxying a physical controller on the client.

The target state is a Windows host that can expose a host-side virtual USB DualSense while synchronizing its state with a remote physical controller connected to the `Shadow` client. The host must also retain a compatibility path for XInput-only games.

## Goals

- Add a Windows host-side `Virtual USB DualSense` path to Sunshine.
- Preserve an `XInput compatibility` path for games that only handle Xbox controllers.
- Treat the remote physical controller as an input/output peer, not as the host-side device itself.
- Keep the Sunshine core input model platform-agnostic.
- Make `Shadow` the canonical high-fidelity client for DualSense transport.

## Non-Goals

- Do not replace the client-side physical controller with host-side haptics only.
- Do not attempt to force a single emulation mode to satisfy both XInput-only titles and DualSense-native titles.
- Do not block the full design on USB audio support. USB audio is a future extension, not a phase-1 requirement.
- Do not require macOS implementation before Windows architecture is stable.

## Key Decision

Windows uses a dual-path strategy:

- `xinput_compat`: preserve the current ViGEm-backed compatibility path.
- `dualsense_usb`: add a new host-side virtual USB DualSense path.

The default must remain conservative. `auto` should prefer compatibility unless the user or per-app configuration explicitly selects native DualSense emulation.

## Definitions

- `Shadow`: the custom client that runs on iPadOS and reads a physical DualSense through GameController APIs.
- `Host virtual device`: the Windows-side device created by Sunshine infrastructure and exposed to the OS.
- `Physical device`: the actual DualSense paired to the client over Bluetooth.
- `Device model`: the shared representation of buttons, sticks, triggers, touch, motion, battery, LED, and trigger effects.
- `Pad service`: a Windows service or helper process that mediates Sunshine and the virtual USB driver.

## Architecture

### 1. Sunshine Core

Sunshine core remains responsible for:

- receiving controller arrival and state updates from the client
- tracking controller slots per session
- routing touch, motion, and battery events
- routing feedback messages back to the client

Sunshine core must not know whether the host-side device is ViGEm-backed or virtual-USB-backed.

### 2. Windows Gamepad Backend Layer

Introduce an explicit backend abstraction inside the Windows platform layer.

Required interfaces:

- `IWindowsGamepadBackend`
- `IWindowsGamepadDevice`

`IWindowsGamepadBackend` responsibilities:

- health/probe
- supported emulation modes
- device creation and removal
- installation and diagnostics metadata

`IWindowsGamepadDevice` responsibilities:

- apply button and axis state
- apply controller touch
- apply motion samples
- apply battery state
- surface output feedback generated by the host

### 3. Windows Backends

#### VigemLegacyBackend

Purpose:

- preserve current behavior for `x360` and `ds4`
- keep existing users working during migration

Responsibilities:

- host `xinput_compat`
- optionally keep `ds4_legacy` if still useful for testing

#### DualSenseUsbBackend

Purpose:

- present a host-side virtual USB DualSense to Windows

Responsibilities:

- create and destroy a host-side virtual USB DualSense device
- update input reports from Sunshine controller state
- receive output reports from Windows applications
- forward output semantics back to Sunshine feedback queues

### 4. Windows Driver Stack

The new backend is composed of two layers:

#### DSUSB Driver

Windows driver that owns the virtual USB device.

Requirements:

- enumerate as a DualSense-like USB device
- expose a HID interface with the required report descriptor
- support output reports for rumble, LED, and trigger effects

Phase-1 target:

- `DSUSB-Lite`

`DSUSB-Lite` includes:

- standard gamepad input
- touchpad input
- motion input
- battery state
- handle rumble
- LED updates
- adaptive trigger output reports

Deferred:

- composite USB audio path
- advanced audio-backed haptics

#### Sunshine Pad Service

User-mode Windows service or helper that mediates Sunshine and the driver.

Responsibilities:

- device lifecycle
- IPC bridge between Sunshine and the driver
- health reporting
- installation checks
- log collection and diagnostics

Reasoning:

- keeps Sunshine process simpler
- isolates Windows driver lifecycle complexity
- provides a single place for admin-sensitive operations

### 5. Shadow Client Role

`Shadow` does not create the host-side device. `Shadow` acts as the remote front-end of the host-side virtual DualSense.

Inbound to host:

- controller arrival metadata
- button and axis state
- touchpad events
- motion samples
- battery state

Outbound from host:

- rumble
- trigger rumble
- motion enable/report-rate requests
- RGB LED changes
- adaptive trigger commands

### 6. Shared Device Model

Create a shared `DualSense device model` in Sunshine that is independent of transport and host backend.

This model must own:

- logical button mapping
- axis normalization
- touch coordinate mapping
- motion axis conventions
- battery mapping
- RGB LED state
- adaptive trigger effect payload handling

This model is reused by:

- `DualSenseUsbBackend`
- future macOS `HIDVirtualDevice` backend
- tests

## Shadow Contract

This section is the normative contract for the custom client.

### Arrival

Shadow sends controller arrival metadata once the physical DualSense is available.

Required values:

- `type = LI_CTYPE_PS`
- `supportedButtonFlags` must reflect the physically available controls
- `capabilities` must reflect what the client can actually deliver and apply

Expected capability mapping for iPadOS + Bluetooth DualSense:

- `LI_CCAP_ANALOG_TRIGGERS`
- `LI_CCAP_RUMBLE` if handle haptics are available
- `LI_CCAP_TRIGGER_RUMBLE` if trigger haptics localities are available
- `LI_CCAP_TOUCHPAD` if GameController exposes DualSense touchpad input
- `LI_CCAP_ACCEL` if accelerometer data is available
- `LI_CCAP_GYRO` if gyroscope data is available
- `LI_CCAP_BATTERY_STATE` if battery state is readable
- `LI_CCAP_RGB_LED` if controller light control is available

### State Stream

Shadow sends:

- `buttonFlags`
- `lt`
- `rt`
- `lsX`
- `lsY`
- `rsX`
- `rsY`

These are the canonical live state values for the host-side virtual device.

### Touch Stream

Shadow sends controller touch events only for controller touchpad interactions.

Requirements:

- stable `pointerId`
- normalized `x` and `y` in `0..1`
- `pressure` normalized in `0..1`
- proper down, move, up, and cancel semantics

### Motion Stream

Shadow must send motion only when the host explicitly requests it.

Requirements:

- accelerometer in `m/s^2`, inclusive of gravity
- gyroscope in `deg/s`
- report rate bounded to what the client can sustain reliably

### Battery Stream

Shadow sends:

- battery state
- battery percentage when available

Battery updates should be sent on connect and on meaningful changes.

### Feedback Application

Shadow must apply host feedback to the physical controller:

- rumble
- trigger rumble
- RGB LED
- adaptive trigger effects

If a capability is unavailable at runtime, Shadow must no-op cleanly and log the downgrade.

### Shadow-Specific Metadata Extension

Add a Shadow-specific metadata block outside the base Limelight capability bits.

Suggested fields:

- `physical_device = dualsense`
- `physical_transport = bluetooth`
- `supports_adaptive_triggers`
- `supports_handle_haptics`
- `supports_trigger_haptics`
- `supports_motion`
- `supports_touchpad`
- `supports_rgb_led`

This metadata is not required for core functionality, but it is useful for diagnostics and future routing decisions.

## Emulation Modes

### auto

Default mode with conservative fallback behavior.

Behavior:

- use `xinput_compat` unless explicitly overridden
- allow per-app override to `dualsense_usb`

### xinput_compat

Compatibility-first mode for Windows games that only behave correctly with Xbox semantics.

### ds4_legacy

Optional legacy/testing mode preserved during migration. Not a strategic end-state.

### dualsense_usb

Native host-side virtual USB DualSense mode.

This is the primary strategic target of this blueprint.

## Configuration Model

The current `gamepad` config key is too narrow for the final state.

Target configuration shape:

- `gamepad_mode = auto|xinput_compat|ds4_legacy|dualsense_usb|off`
- `gamepad_dualsense_usb_profile = lite|full`
- `gamepad_xinput_fallback = enabled|disabled`
- `gamepad_per_app_overrides`

The UI and API must become backend-aware instead of ViGEm-specific.

## UI and Diagnostics

Replace the current ViGEm-only troubleshooting experience with driver-aware diagnostics.

Required diagnostics:

- `Vigem legacy backend` health
- `DualSense USB backend` health
- `pad service` health
- install status for each backend
- selected mode
- effective mode after per-app resolution

The current `/api/vigembus/*` endpoints should eventually be superseded by a generalized `gamepad backend` status surface.

## Done Criteria

The Windows Virtual USB DualSense effort is only considered complete when all of the following are true:

- Sunshine can expose a host-side virtual USB DualSense on Windows.
- Shadow can drive that host-side device from an iPad-connected physical DualSense.
- Host-generated output effects return to the physical controller.
- XInput compatibility remains available as a separate mode.
- The Windows UI and diagnostics are backend-aware rather than ViGEm-only.
- The implementation is covered by tests and a manual validation checklist.

## DSUSB Build and Install Notes

The repository now contains:

- a user-mode/backend path in Sunshine that selects `dualsense_usb`
- a named-pipe pad service client
- a `sunshinepadsvc` server skeleton
- a DSUSB bus driver skeleton that accepts IOCTLs
- a split between bus control and UDE-backed device creation
- a minimal DualSense descriptor skeleton

What this means in practice:

- the control plane exists
- the process boundaries exist
- the IOCTL contracts exist
- the service and backend can talk to each other
- the driver can accept commands and store per-slot state

What is still missing is the actual UDE-backed USB device creation and the real DualSense output report path.

### Driver Installation

Current starter assets:

- `drivers/windows/dsusb/dsusb_bus.inf`
- `src_assets/windows/misc/dualsense-usb/install-dsusb-driver.bat`
- `src_assets/windows/misc/dualsense-usb/uninstall-dsusb-driver.bat`

Current behavior:

- the batch script accepts either the `.inf` path or the raw `.sys` path
- `.inf` install path uses `pnputil /add-driver ... /install`
- raw `.sys` install path creates/starts the `SunshineDualSenseBus` kernel service

This is only a starter path. Real Windows deployment still needs:

- a signed driver package
- packaging integration with the Sunshine Windows artifacts
- a decision on whether installation is owned by setup scripts or the final installer

### Pad Service Runtime

Current starter assets:

- `tools/sunshinepadsvc.cpp`
- `src_assets/windows/misc/dualsense-usb/start-pad-service.bat`
- `src_assets/windows/misc/dualsense-usb/stop-pad-service.bat`

Current behavior:

- Sunshine can auto-launch `sunshinepadsvc.exe` when the named pipe is absent
- the service exposes command and feedback named pipes
- the service forwards commands into the DSUSB bus contract
- the service reports backend availability, installed state, service-running state, and driver version

### What Works Today

- Sunshine can select a `dualsense_usb` backend
- Sunshine can auto-launch `sunshinepadsvc.exe`
- `sunshinepadsvc` accepts create/destroy/update commands over named pipes
- `sunshinepadsvc` forwards those commands into the DSUSB bus contract
- the DSUSB bus driver skeleton accepts IOCTLs and stores per-slot state
- the UDE layer is split out behind `DsUsbUde*` functions
- a descriptor skeleton exists for the future virtual device path

### What Is Still Missing

#### 1. Real UDE Device Creation

`drivers/windows/dsusb/dsusb_ude_device.c` currently stores metadata only. It does not create an actual UDE root, USB device, interface, or endpoints.

Needed work:

- create a per-slot UDE object model
- register the USB device with UDE
- bind the descriptor set to the device
- expose interrupt IN and OUT endpoints
- manage per-slot lifecycle and teardown

#### 2. Real DualSense HID Report Model

The HID descriptor is intentionally minimal.

Needed work:

- replace the skeleton report descriptor with a report layout that matches the intended DualSense emulation target
- define stable input report structures
- define output report structures for:
  - rumble
  - RGB LED
  - adaptive trigger effects
- map Sunshine state into those reports

#### 3. Output Report Path

The current driver does not yet capture host output reports and push them back to `sunshinepadsvc`.

Needed work:

- collect output reports from the HID OUT endpoint
- translate them into the service feedback protocol
- forward them through the feedback named pipe
- validate the end-to-end path:
  `game -> driver -> sunshinepadsvc -> Sunshine -> Shadow`

#### 4. Driver Packaging

The INF and batch scripts are a starting point only.

Needed work:

- sign the driver package
- package `dsusb_bus_driver.sys` and `dsusb_bus.inf` with the Windows build artifacts
- decide whether installation should be driven by:
  - `pnputil`
  - a setup script
  - the existing `sunshine-setup.ps1`
  - a future Windows installer step

#### 5. Build Integration

The repository includes driver source but does not yet build it.

Needed work:

- add a WDK-capable build path
- decide whether the driver builds through:
  - a Visual Studio / WDK project
  - MSBuild invoked from CI
  - a separate driver-only workflow
- document local build requirements

## Practical Testing Checklist

When the real UDE path is implemented, validate in this order:

1. `sunshinepadsvc.exe` starts and creates both named pipes
2. `dualsense_usb` backend reports available in `/api/gamepads/backends`

   - rumble
